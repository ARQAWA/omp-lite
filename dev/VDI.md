## Правило запуска

**Программу из поставки расширение запускает только так:**

```text
node-pty из VS Code
  -> powershell.exe -NoLogo -NoProfile -Command "& 'C:\Program Files\Git\bin\bash.exe' --login -i -c '<команда>'"
     -> Git Bash
        -> программа
```

1. `node-pty` берётся из самого VS Code: `<appRoot>/node_modules.asar/node-pty`, иначе `<appRoot>/node_modules/node-pty`.
2. `<команда>` — строка для bash. Каждый аргумент в одинарных кавычках. Кавычка внутри аргумента пишется `'\''`.
3. Вся `<команда>` для PowerShell стоит в одинарных кавычках. Каждая кавычка внутри удваивается.
4. В путях только прямые слеши: `C:/Users/x/file`. Двойной обратный слеш разборщик Git Bash сворачивает в один.
5. Двойных кавычек в `<команда>` нет: PowerShell 5.1 их не передаёт дальше.
6. Секреты идут только через окружение, не через строку команды.
7. Второго bash и файла-обёртки перед программой нет.

**Запрещено:** `child_process.spawn`, `exec`, `execFile` для программ из поставки (`omp.exe`, `bun.exe`, `llama-server.exe` и любых новых).
С 0.0.6 в ompcli таких программ две: `omp.exe` и `llama-server.exe`. Установка харнеса и распаковка обновления идут внутри extension host, без программ.
Extension host сам запускает только две вещи: `curl.exe` из `System32` (видел: работает) и сам VS Code как Node (так делает CCLI; код).

Так запускают все три расширения: PCLI `pi.exe`, CCLI `codex.exe`, ompcli `omp.exe` и `llama-server.exe`.
Носители в коде: `bashCommand`, `chatCommand`, `bundledStarter`, `bundledChild` в `src/modules/ompcli/index.js`.
Образец: `~/ai-project/my-pi/pcli-vscode/extension.js`, функция `makePty`. Владелец сказал «как PCLI»? Сначала прочти образец и повтори форму буквально.

## Что известно о VDI

1. **видел** — прав администратора нет. Git Bash работает.
2. **видел** — PCLI работает: `pi.exe` стартует цепочкой из раздела выше. На VDI стояла версия 0.0.2 (27.10), позже новее.
3. **видел** — ompcli 0.0.3: `fetch failed` на загрузке модели. Потом `curl: (22) ... error: 502`. Потом загрузки прошли и вышло `spawn EPERM`.
4. **видел** — ompcli 0.0.4 с программами в каталоге расширения: снова `spawn EPERM`.
5. **видел** — ompcli 0.0.5, запуск цепочкой: `bash: c:/Users/.../arqawa.ompcli-0.0.5-win32-x64/runtime/bun.exe: Permission denied`. Значит, цепочка `node-pty` -> PowerShell -> Git Bash на VDI работает, кавычки и пути доходят верно, а запрещён сам файл `bun.exe`.
5a. **видел** — `curl.exe` из `System32` прямым запуском из extension host работает: им скачались файлы.
6. **видел** — в PCLI колесо листало историю ввода, а не чат. В CCLI листало верно.
7. **видел** — Ctrl+V вставляет текст, но не картинку. Alt+V вставляет картинку, но не на русской раскладке.
8. **видел** — после выключения `terminal.integrated.enableKittyKeyboardProtocol` терминал заработал.
9. **видел** — веб-поиск в Pi на VDI не работал. Со слов агента на VDI: `read ECONNRESET`.
10. **догадка, со слов агента Pi на VDI** — VS Code запускается через `vsc.cmd`. Он поднимает локальный прокси на `127.0.0.1:8317` и ставит `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY`, `NODE_USE_ENV_PROXY=1`. Настройка VS Code `http.proxy` при этом пуста. VS Code, открытый без `vsc.cmd`, прокси не получает.
11. **догадка** — ограничение дочерних процессов VS Code, нет WSL. Так записано в решениях PCLI, исходной цитаты владельца не нашли.
12. **догадка** — память VDI: 32, 48 или 64 ГБ. Владелец точно не помнит.

## Чего не знает никто

1. **Почему запрещён именно `bun.exe`.** Версия 0.0.5 назвала файл: отказ даёт сам `bun.exe`, и прямым запуском, и цепочкой. `pi.exe` из такого же каталога расширения работает. Правило, которое их различает, неизвестно.
2. **Какая защита стоит на VDI.** AppLocker, WDAC, Defender ASR, EDR: журналы никто не смотрел.
3. **Пустит ли VDI `omp.exe` и `llama-server.exe`.** PCLI доказывает цепочку только для `pi.exe`. Отказ `llama-server.exe` вкладку не закрывает: OMP откроется без памяти и назовёт причину.
4. **Работает ли ompcli 0.0.6 на VDI.** До первого запуска владельцем ответа нет.
5. **Версии на VDI:** Windows, VS Code, его `node-pty`, Git for Windows, профиль bash.
6. **Первый сбой PCLI.** Владелец помнит похожую ошибку и починку. Сессия не найдена. Первая версия PCLI в git уже шла цепочкой.
7. **Старый `omp-vscode`** качал `omp.exe` в `globalStorage` и запускал цепочкой. Работал ли он на VDI, записей нет.

Что известно по документации Windows:

1. libuv даёт `EPERM` на отказ в доступе (коды 5 и 1314). Node бросает такую ошибку сразу, без имени файла.
2. Политика может различать программы по издателю, пути и хешу. Защита может смотреть и на родителя процесса.
3. Было два объяснения: режут прямой запуск из VS Code или режут сам файл. Версия 0.0.5 показала второе: файл `bun.exe` запрещён и при запуске из Git Bash.

## Опровергнутое

0. **«Цепочка PCLI пустит `bun.exe`».** Версия 0.0.5 запустила его цепочкой и получила `Permission denied`. Решение D-050 оставлено для `omp.exe` и сервера памяти, `bun.exe` убран в D-052.

1. **«Запрещён запуск из `AppData`, из каталога расширения можно».** Версия 0.0.4 перенесла программы и упала так же. Решение D-049, причина снята в D-050.
2. **«`fetch failed` значит, что прокси не задан».** Сказано слишком уверенно. Точно известно одно: Node `fetch` не читает ни `http.proxy`, ни окружение.
3. **«PCLI не ходит в сеть на VDI».** Его `Update` ходит в GitHub.

## Что код ompcli берёт на веру

На Windows это не запускалось. Проверено по исходникам и на macOS с настоящими bash и Bun.

1. PowerShell 5.1 передаёт строку в одинарных кавычках без изменений.
2. Разборщик Git Bash не трогает одинарные кавычки и одиночные обратные слеши внутри внешних двойных.
3. `MSYS_NO_PATHCONV=1` выключает переделку аргументов. Git for Windows это описывает. Стоит только у скрытых запусков.
4. Профиль bash не меняет рабочую папку и не стирает `PATH`. Гарантии нет: профиль у каждого свой.
5. Закрытие `node-pty` убивает программу внутри. Microsoft обещает это для процессов, привязанных к консоли.
6. PowerShell превращает любой код ошибки программы в `1`. Причину отказа несут последние строки терминала, не код.
7. `omp.exe` и `llama-server.exe` понимают пути с прямыми слешами.

Пункты 1 и 2 версия 0.0.5 подтвердила на VDI: путь к `bun.exe` дошёл до bash без искажений.
