# Обновление харнеса omp-lite на другую версию OMP

Скилл не привязан к версиям: `<old>` это версия из `INSTALL.md`, `<new>` это целевая. Между ними может быть любое число релизов: сверка идёт напрямую `<old>` против `<new>`, промежуточные не шагаются. Историю прошлых прогонов держит `dev/DECISIONS.md`, не скилл.

OMP этот скилл не загружает: агент приходит по строке в `AGENTS.md`. Механику OMP читай только в исходниках (`AGENTS.md`, правило 36 в `dev/PROCESS.md`). Выпуск VSIX ведёт навык `release-ompcli-vsix`, слепое ревью ведёт `skill://reviewer/SKILL.md`: они даны ссылкой.

Сторож пишет «native … changed description», после `omp update` харнес ведёт себя иначе или `omp --version` не равен `INSTALL.md`: это смена версии. Апдейт идёт целиком по чек-листу, не точечной правкой.

## Правила владельца

1. минимум кода, тестов и строк: «самый микро- микро-нано-минимальный, минимально достаточный».
2. ни одна механика харнеса не ломается.
3. ничего сверх заказа: без отсебятины, доработок и выбрасываний без согласия владельца.
4. сначала план и ревью плана. Принятый план собирай сразу, без вопроса.
5. блокер и крит не останавливают работу. Запиши его в `ROADMAP.md` и сделай всё, что от него не зависит. К владельцу иди один раз, когда независимой работы не осталось: все блокеры и криты одним списком, каждому вопрос да или нет и что уже готово.
6. доказательство всегда полное: `scan`, `verify`, `probe` идут целиком при любом размере апдейта.
7. ревью по стадиям: каждое закрывает свой этап и проверяет только его. В конце одно лёгкое ревью согласованности этапов. Сплошной проверки всего подряд нет.
8. живые пробы только на дешёвых моделях: список в `contract.json`, ключ `probes`.
9. модели. Апдейт ведёт `openai-codex/gpt-6.2-sol:medium`: разбор, план, задания, приёмка. Правки и установку делает сабагент `openai-codex/gpt-6.1-terra:max` по заданию главной: [references/task.md](references/task.md). Код-ревью: `openai-codex/gpt-6.2-sol:low`. `acceptor` берёт модель из профиля. Отработавшего сабагента гаси: `write`, `path: proc://<id>/kill`, `content: ""`.
10. VSIX выпускай сразу после доставки, без вопроса.
11. обновляй всё вокруг (правило 38 в `dev/PROCESS.md`).
12. `commit` через `eval` остаётся включённым: `commit.enabled: false` не писать.
13. отчёты короткие, простой русский на «ты», главное жирным.

## Скрипты

Лежат в `scripts/`, запуск из корня worktree: `S=dev/agents/omp-upgrade/scripts`. Временная папка `/tmp/omp-up` (переменная `OMP_UP`). Исходники OMP скрипты читают сами: `git show v<версия>:<путь>` из `~/ai-project/omp-src`, клон не переключается.

|команда|что делает|меняет|
|---|---|---|
|`bun $S/scan.js <old> <new>`|берёт оба бинаря из релиза по хешу, гоняет харнес worktree на обоих, пишет `/tmp/omp-up/scan.md`|ничего|
|`bun $S/bump.js <old> <new>`|версия во всех местах, пин `omp.exe` из релиза, версия расширения +1|worktree|
|`bun $S/reference.js <new>`|эталон сторожа из родного снимка `<new>`|worktree|
|`bun $S/verify.js`|ворота согласованности worktree; `--runtime`: ещё стоящий OMP и `~/.omp/agent`|ничего|
|`bun $S/probe.js`|живые пробы стоящего харнеса на дешёвых моделях и интерфейс; пишет `/tmp/omp-up/probe.md`|ничего|

Что скрипты проверяют, записано в `contract.json`: опоры харнеса на исходники OMP, тексты в запросе, открытые провайдеры, пин. Новая механика харнеса, которая опирается на OMP, получает там строку.

## Чек-лист

До приёмки плана репозиторий и рантайм не меняются. Журнал веди в `/tmp/omp-up/ROADMAP.md`: цель, слова владельца, галочки этапов, список блокеров и критов. После компакта читай его целиком.

### 1. версии и worktree

- [ ] `<old>`: строка `omp/<версия>` в `INSTALL.md`. `<new>`: `omp update --check`. Версию назвал владелец: бери её.
- [ ] у `<new>` есть релиз: `gh api repos/can1357/oh-my-pi/releases/tags/v<new> --jq .tag_name`. Релиза нет: это блокер. Разбор и план веди на последнем выпущенном релизе.
- [ ] worktree от свежего `main`: `git status --short && git pull -q --ff-only && git worktree add -q -b omp-<new-через-дефис> ../omp-lite-worktrees/omp-<new-через-дефис> main`. Все правки только там.

### 2. разбор

- [ ] `bun $S/scan.js <old> <new>`, прочитай `/tmp/omp-up/scan.md` целиком.
- [ ] прочитай изменения OMP: `git -C ~/ai-project/omp-src diff v<old> v<new> -- '*CHANGELOG.md'`. Ищи то, чего нет в отчёте: новые тексты в запросе, новые настройки по умолчанию, смену поведения тулов.
- [ ] каждую строку разделов «изменилось» и «новое» открой: файлы сравнения названы в строке, исходники `<new>` лежат в `/tmp/omp-up/src-<new>`.

### 3. план и его ревью

- [ ] `/tmp/omp-up/PLAN.md`: таблица «строка отчёта, решение, класс, файл, доказательство». Классы и типовые решения: [references/risk.md](references/risk.md).
- [ ] ревью плана: [references/reviews.md](references/reviews.md), стадия «план».
- [ ] итог владельцу без вопроса: план принят, сборка идёт. Всё вне плана только вопросом.

### 4. сборка

- [ ] `bun $S/bump.js <old> <new>`.
- [ ] в отчёте сломан эталон сторожа: `bun $S/reference.js <new>`.
- [ ] правки R1 по плану: задание сабагенту по [references/task.md](references/task.md). Минимально, тесты зеркалят правку.
- [ ] запись D в конец `dev/DECISIONS.md` по форме последней записи про апдейт OMP.
- [ ] `bun $S/verify.js` запусти сам после сабагента: все строки PASS. Строка FAIL, которая в `scan.md` стоит в разделе «долг», не от этого апдейта: это крит R2.
- [ ] код-ревью: [references/reviews.md](references/reviews.md), стадия «сборка».
- [ ] коммит в ветке: `omp-<new>: харнес на OMP <new> (D-<номер>)`. Merge пока нет.

### 5. Mac

- [ ] `omp update`, затем `omp --version`: ровно `omp/<new>`. Другая версия: не ставь, это блокер.
- [ ] установка по `INSTALL.md` из worktree: [references/delivery.md](references/delivery.md).
- [ ] `bun $S/verify.js --runtime`: все строки PASS, кроме долга.
- [ ] `bun $S/probe.js`: ни одной строки FAIL. «PASS, сбой модели» это норма: шаг не сделала одна модель, другие сделали.

### 6. доставка

- [ ] ревью согласованности: [references/reviews.md](references/reviews.md), стадия «согласованность».
- [ ] `omp update --check` ещё раз. Вышла новая версия: это блокер, текущую доставку доведи до конца.
- [ ] merge fast-forward, push, рантайм из `main`, уборка, VSIX, всё вокруг: [references/delivery.md](references/delivery.md).
- [ ] отчёт владельцу: что сделано, числа `verify` и `probe`, блокеры и криты R2 одним списком, каждому вопрос да или нет.

## Типичные ошибки и подводные камни

1. целевая версия это то, что отдаёт `omp update --check`. Свежий тег бывает без релиза и без бинарей: `omp update` поставит прежнюю.
2. `api.github.com` без входа даёт 60 запросов в час. Релиз читай через `gh api`: скрипты так и делают.
3. новые провайдеры открыты по умолчанию, белого списка в OMP нет. `scan` показывает их строкой «провайдер … (открыт)»: закрывай в `disabledProviders` и правь число в README `rqw-runtime-config`.
4. OMP может сам добавить текст в запрос. `scan` покажет «системный промпт другой» или «описание … другое». Ищи штатную настройку в исходниках `<new>`, проверь её повторным `scan`. Текст можно и оставить: это крит R2.
5. обход OMP может умереть сам: OMP начал делать то же штатно. Доказывай снимком с обходом и без, удаляй обход только по плану.
6. «опора … менялся» в отчёте значит: файл исходников другой, а наша проверка по нему ещё проходит. Прочитай дифф файла: проверка смотрит одну строку, смысл мог уехать.
7. родные тексты меняют и маркеры `{ "native": ... }` в `rqw-base-tools.texts.json`. После `reference.js` гоняй `bun test dev/tests`: тест сторожа назовёт маркер.
8. якоря `EDITS.task` и `EDITS.eval` сверяются с отрендеренным текстом, не с шаблоном `prompts/tools/*.md`. Отрендеренный текст лежит в снимке `/tmp/omp-up/cap-<версия>-native.json`.
9. `Update` во вкладке VDI отказывает на новом `runtime.json`: VDI получает новый OMP только новым VSIX. Поэтому `bump.js` поднимает версию расширения вместе с пином.
10. `scan` и `verify` видят только встроенный каталог моделей. Живой каталог (модели по входу) проверяет `probe`, строка «модели конфига есть в живом каталоге».
11. `verify --runtime` требует равенства рантайма worktree. До установки он красный: это не находка.
12. блок из `AGENTS.md` переключает `~/ai-project/omp-src` на тег стоящей версии. Скриптам это не мешает: они читают по тегу. Руками в клоне ничего не удаляй и не переключай.
13. политика `bash` блокирует `grep`, `ls`, `cat`, `head`, `tail`, `find`, `sed -n`, даже внутри пайпа. Читай `read`, ищи `grep` и `glob`.
14. сторож `eval` блокирует код с текстом `agent(` и `workpool(`. Пиши это в Contract заданий сабагентам.
15. сабагентам давай абсолютные пути worktree и запрет трогать основной каталог. После каждого: `git -C <основной> status --short`.
16. у сабагентов нет `manage_skill`: навыки в `managed-skills` обновляет главный. `task` с `agent: scout` и `model` даёт отказ: модель задавай без `agent`.
17. одно blind review за раз. Между кругами работа заморожена.
18. ревьюер считает лишним всё сверх слов владельца. Записи в `.omp/inventory/` защищай правилом проекта.
19. при слиянии конфига по `INSTALL.md` старый `config.yml` разбирай `Bun.YAML.parse`: PyYAML его не читает. YAML не дописывай через `echo` в шелле.
20. `omp -p` пишет `Working...` в stderr: это норма. `omp config get` корневого ключа даёт «Unknown setting»: спрашивай листья или `omp config list --json`.
21. выпуск VSIX пишет свою запись D прямо в `main`. Номер своей записи бери после него или до него, не одновременно.
22. Marketplace проверяет VSIX около 15 минут: до конца проверки версии в ответе нет.
